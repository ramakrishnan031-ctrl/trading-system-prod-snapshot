# Is the EOD capture path safe to point live traffic at?

**READ-ONLY safety assessment.** 2026-07-24 (IST). Deployed HEAD: `bc75406`. Code + config read; DB `mode=ro&immutable=1`. **No test POST was sent to the receiver** (§1.1); no evidence producer run; no config/flag change; service not restarted. This examines the EOD-capture path inside the webhook receiver before a Chartink EOD scan is pointed at it.

---

## VERDICT (the three lines)

> **1. NOT YET — pointing traffic at it is safe FOR THE RECEIVER, but a capture that mistimes or fails is lost SILENTLY.** The ingress handling is contained (async `put_nowait`, multi-layer try/except, bounded queue, the broker fetch runs off the request thread, and an "eod" scanner `return`s before the kill/window gates and never touches the intraday `signal_queue`) — it **cannot disturb live signals or the receiver.** But per §0's decision rule, two silent-failure modes gate the go: **timing** (a POST outside the window is silently dropped) and **observability** (a failed capture emits only a log line — no alert, no heartbeat). So: **create the scan only once (a) its firing time is pinned to the safe window and (b) you commit to the morning-after check.**
> **2. Latest a POST can arrive and still be captured: after 15:30 and comfortably before 16:00 IST — target the ~15:35–15:50 window on a trading day.** Lower bound **15:30** (`market_close`; earlier, the breakout is an unsettled/forming session and the capture is SKIPPED). Upper bound **16:00** (`SERVICE_WINDOW_END`, main.py:1594 — the service self-exits when flat; after that the connection is refused). Leave margin below 16:00 for the rate-limited per-symbol daily fetch to drain before the self-exit. (MEASURED bounds; the drain margin is ASSUMED to scale with symbol count.)
> **3. How you'd know it worked: a read-only check the next morning — `SELECT * FROM pb01_watchlist WHERE trading_date = <today>`.** Rows present ⇒ captured. There is **no Telegram, no heartbeat, and no alert on failure** — success is a log line + a DB row, failure is a log line only. If nothing appears, you cannot tell "no breakouts" from "capture failed" without reading the logs.

## §2 — Failure containment (quoted)

- **§2.1 — `submit()` is ASYNC, not synchronous.** The receiver calls `self._eod_capture.submit(...)` (`webhook_receiver.py:728`), and `submit()` is a non-blocking enqueue: `self._q.put_nowait((scanner_name, symbol, triggered_at))` (`watchlist_capture.py:106`). The heavy work — the broker daily fetch + `compute_breakout_level` + insert — runs in the background worker `_capture` (`:131-173`), off the request thread. (MEASURED.)
- **§2.2 — exceptions are caught at every layer** (quoted, not inferred): the receiver wraps the submit call — `except Exception … "a capture-submit error must never break the response"` (`webhook_receiver.py:731-732`); `submit()` catches `queue.Full` → returns False, logged (`watchlist_capture.py:108-113`); the worker loop catches per-item — `except Exception … "one broken symbol must NEVER kill the worker"` (`:126-127`); and the fetch has its own try/except (`:187-189`). The response is **200 regardless of the submit outcome** (`:735`).
- **§2.3 — shared resources (enumerated, not denied):** the capture path shares with the live path: **(1) the DB `store`** — but an INSERT-only write to a *separate* table (`pb01_watchlist`, `UNIQUE(symbol,trading_date)` dedupe), not the trades/orders tables; **(2) the "historical" rate-limiter** — the capture fetcher reuses `_sr_fetch_fn` (main.py:3084,3101), the *same* `rate_limiter.acquire("historical")` bucket the live sr_detector uses (main.py:426); **(3) the `instrument_cache`** (read-only lookup); **(4) a receiver worker thread** — held only for the parse + `put_nowait` (microseconds), the broker call is elsewhere; **(5) `market_windows`** (read-only). The one shared *live-fetch* resource is the historical rate limiter — an EOD burst consumes its tokens — but the capture runs **after 15:30 close**, when the live S&R path is not fetching for intraday signals, so contention is minimal. (MEASURED wiring; the low-contention conclusion is ASSUMED from the post-close timing.)
- **§2.4 — return codes:** 200 on success and on watchlist-disabled (`:722,:735`); **400** malformed JSON / missing `stocks`/`trigger_prices`/`triggered_at` / bad `triggered_at` (`:700-713`); **404** unknown scanner (`:499`); **401** bad/absent auth (`:481-494`). A valid, authed, known-eod POST always gets 200 ⇒ **no non-200 retry storm** on the normal path; misconfigurations get an explicit 4xx (terminal client errors Chartink does not storm on).
- **§2.5 — nothing unbounded:** the queue is bounded (`maxsize=256`, `:76`), and `put_nowait` drops (returns False, logged) when full — a fail-safe miss, never a retry loop or memory growth (`:108-110`). The worker processes one item at a time.

## §3 — The broker call and the timing

- **§3.1 — the broker call is real, and off the request thread (CONFIRMED — the §3.1 hypothesis holds).** `_capture` fetches daily candles via the injected fetcher → `_sr_fetch_fn` → `market_kite.historical_data(...)` (main.py:423-432). **Per-symbol** (the worker dequeues one symbol at a time), so a 30-symbol alert = 30 sequential fetches. **§3.1.2 rate limits:** every fetch first `rate_limiter.acquire("historical")` (main.py:426) → paced (≤ the historical bucket, ~3/s), never bursted; on a rate-limit or any `historical_data` error the fetcher logs and returns `{}` (`sr_detector/fetch.py:133`) → `compute_breakout_level([])` → None → **skip capture** (fail-safe, `watchlist_capture.py:151-155`). **§3.1.3 token:** if the market-data kite handle is absent, `_fetch` returns `[]` (main.py:424-425) → skip; an expired token makes `historical_data` raise → caught → `{}` → skip. Either way **fail-safe, logged, no crash.** **§3.1.4 latency:** because `submit()` is `put_nowait`, a slow broker delays *captures* (in the single background worker) but **never holds a receiver thread** — the receiver pool cannot be starved by a slow broker here.
- **§3.2.1 — the window.** `SERVICE_WINDOW_END = _time(16, 0)` IST (main.py:1594); the self-exit thread sets `shutdown_event` and exits 0 once past 16:00 **and flat** (main.py:1134-1168), auto-restarting ~08:15 next day. `market_close = 15:30` (system_config.yaml:51). **Safe arrival window = [15:30, ~16:00) on a trading day**, targeting **~15:35–15:50** for drain margin.
- **§3.2.2 — the EOD route does NOT check the clock.** `_handle_eod` parses + submits whenever a POST arrives; the timing logic (SETTLED-ONLY, `trading_date`) lives in the background `_capture`.
- **§3.2.3 — a market-hours EOD POST is harmless.** It is accepted (200) but the worker's SETTLED-ONLY guard skips it — `if breakout_date == now.date() and not market_closed(now): SKIP premature` (`watchlist_capture.py:141-146`) — so **no watchlist row is written** (no wrong `trading_date` pollution), and because the EOD route `return`s at `webhook_receiver.py:509` before the kill/window gates and never enqueues to `signal_queue`, **it cannot disturb live signal processing.**
- **§3.2.4 — drain vs the 16:00 exit.** The worker drains continuously, so a POST at, say, 15:45 is fully processed within seconds. The risk is only a POST arriving *very* close to 16:00: on shutdown, `pb01_capture_worker.stop()` (main.py:1339) joins the worker for **3 s** (`watchlist_capture.py:89-98`); if a fetch is still in flight past that, the daemon worker is abandoned on process exit and **that capture is lost** (silently). Hence the margin below 16:00.
- **§3.2.5 — `trading_date` is holiday/weekend-aware.** `trading_date = next_trading_day(breakout_eod 23:59)` (`watchlist_capture.py:159-160`), holiday-aware (`utils/holiday_guard`), so Friday → Monday and holidays are skipped correctly. A post-midnight arrival is moot — the service is down 16:00→08:15, so such a POST hits a refused connection.

## §4 — The contract the receiver already implements (documented, not designed)

- **§4.1 — scanner name: `pb01_breakout_retest`**, registered with `scanner_type: eod` (scan_webhook_map.yaml:81-84); the POST path is `/webhook/pb01_breakout_retest` ("Routing key MUST equal the /webhook/<scanner_name> URL path", :78). Only a scanner whose map entry has `scanner_type: eod` reaches the capture route (`webhook_receiver.py:508`).
- **§4.2 — required payload:** a JSON object with **`stocks`** (comma-separated symbol string), **`trigger_prices`**, and **`triggered_at`** (`webhook_receiver.py:703-714`); any missing → 400. `trigger_prices` is required but the price is **not trusted** — the level is computed from our own daily candles (`watchlist_capture.py:36-47,148-150`). Symbols are alias-mapped (`:726`).
- **§4.3 — mismatch behavior (the most likely misconfiguration):** an *unknown* scanner name → **404** `{"error":"Unknown scanner"}` (`:498-499`) — visible, not silent. ⚠️ But a scanner registered with the *wrong* `scanner_type` (i.e. omitting `scanner_type: eod`) would default to `"intraday"` (`:508`) and be **routed to the live intraday path** instead of the watchlist — a quieter misconfiguration (it would be rejected by the strategy-control/window gates, not captured). The map entry is already correct; the risk is only if it is edited.
- **§4.4 — auth: YES, the same secret.** Auth runs first (`webhook_receiver.py:472-494`): HMAC (`X-Webhook-Signature`) or, when `require_hmac=False` (current), the `?token=` bearer — identical to the trading webhooks — before any EOD routing.

## §5 — Observability (stated plainly)

- **§5.1 — success is visible but not pushed:** a receiver log (`"EOD alert … → N queued for capture"`, `webhook_receiver.py:733`), a worker log (`"pb01 captured %s LEVEL=…"`, `watchlist_capture.py:175-177`), and a `pb01_watchlist` row. **No Telegram, no heartbeat.**
- **§5.2 — failure is SILENT.** Every failure path — queue full, malformed symbol, missing/expired token, insufficient daily history, premature (market-hours) skip, a fetch error — emits **only a log line** (`:109,:127,:135,:142,:152,fetch.py:133`). There is **no Telegram alert, no CRITICAL sentinel, and no heartbeat** (unlike `forward_shadow_record`, which does heartbeat). So a silently-failing capture looks exactly like "no breakouts today." This is the same "looks alive, produced nothing" pattern found five times this week, and it is the strongest reason for the "NOT YET" posture.
- **§5.3 — the morning-after check (read-only):** `SELECT symbol, level, breakout_date, trading_date, status FROM pb01_watchlist WHERE trading_date = <today>;` — rows ⇒ the previous evening captured; then the 09:20–11:00 entry stage stamps each row's terminal `status` (CONSUMED / EXPIRED_WINDOW / INVALIDATED / SKIPPED_GAP), which is the second-morning read.
