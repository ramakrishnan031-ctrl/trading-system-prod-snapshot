# B. M-A2 — SYNCHRONOUS ALERT SENDS

## B1 — Where the synchronous sends happen, and what they block

**⭐ YES, it is on the order and signal path — and ahead of the order.** This is the
finding that moves M-A2 from hygiene to real, and it is written in the code's own words:

```
signals/signal_processor.py:1130   # Telegram alert: INTRADAY SIGNAL (fires before order placement)
signals/signal_processor.py:1131   self._emit_signal_alert(...)
```

The same call sits on all three entry paths — `_process_one` (`:1131`), the gate-release
resume (`:1901`) and the retest resume (`:2196`) — and in every one of them the capital
**reservation is already held** (`reservation_id` is live; the `no_order_placer` branch a
few lines above releases it). So a slow endpoint delays the entry itself, with capital
reserved and with the FIX-067/M-S1 freshly re-anchored price going stale in the gap —
which is precisely what that re-anchor exists to prevent.

Across the live packages there are **55** synchronous `notifier.send(...)` sites in total
(counted, `orders/ capital/ signals/ data/ broker/ screening/ core/ strategies/ allocation/
regime/ main.py`). Besides the entry path they include:

| path | sites |
|---|---|
| **kill** | `capital/kill_switch.py:562` (`soft_kill`, after persist+publish — the kill lands, the CALLER waits), `:801` (IP-403), `:1236` |
| **order / reconciler** | `orders/order_placer.py` ×11 · `orders/order_reconciler.py` ×13 · `sl_breach_monitor.py:185` · `structure_exit_manager.py:333` · `tgt_retry_manager.py:382` · `breakeven_manager.py:365` |
| **feed** | `data/live_feed.py:389` — inside `_on_reconnect`, i.e. on the **kiteconnect reactor thread**, and it runs **before** `self._on_reconnect_cb(now)` → `candle_store.mark_reconnect` + `smart_tgt.on_reconnect` |

⚠️ **`kill_switch._alert_exit_failed` (`:1230-1246`) sends one CRITICAL PER FAILED TRADE

## B2 — What the timeout is today

**The "no timeout, blocks indefinitely" premise is HALF WRONG, and the half that is right
is the more interesting one.**

`requests.post(url, json=payload, timeout=self._timeout)` — `timeout_sec` defaults to
**5.0** and `main.py:2243` never overrides it, so the HTTP call **is** bounded.

What is **not** bounded is `_SlidingWindowRateLimiter.acquire()`: a `while True` poll with
`time.sleep(0.5)` and **no deadline at all**. It is called **once per HTTP attempt**, so a
send makes up to `max_retries+1` unbounded waits. Under a sustained storm above 20 msgs/min
the caller waits with no bound and no fairness.

**The bounded-but-long part, on the shipped config** (`max_retries: 3`,
`retry_backoff_seconds: 2.0`, `rate_limit_per_minute: 20`, one enabled channel —
`TELEGRAM_CHANNEL_SECONDARY` is `enabled: false`):

```
4 attempts x 5 s  +  3 backoffs x 2 s  =  26 s per chat, per send
```

which is the audit's "~26 s retry ladder", now confirmed against the live config. It is
**per chat**, so enabling the secondary channel would double it.

**⭐ The email fallback is NOT in that budget — it is unreachable in production.**
`_send_email_fallback` needs `ALERT_EMAIL_USER`, `ALERT_EMAIL_PASSWORD` and
`ALERT_EMAIL_TO`; the VM `.env` defines **none** of them (it has `ALERT_SMTP_PASSWORD`,
which is the *alert_watcher's* variable, a different consumer). So the method returns at
its missing-credentials branch (`:681-685`) **before any socket operation**, and the
`smtplib.SMTP(..., timeout=15)` ladder never runs. Recorded as a side finding: **the
CRITICAL Telegram→email fallback is inert; the alert_watcher sentinel path is the actual
backup.**

## B3 — Timeout, not async

A **timeout**, per the batch's steer and for a concrete reason: async dispatch would
reintroduce exactly the publish-then-read race documented in M-O9 last session, on the
alerting path, the weekend before PB-01 goes live. A deadline needs no new thread, no
queue, and no ordering assumption.

**Giving up early costs no alert** — this is what makes the timeout safe rather than a
trade-off. `_handle_critical` writes the sentinel **first** (TG5) before any HTTP, so the
alert_watcher email path is already armed when the deadline bites; `_handle_error` still
writes `failed_alerts.log`. Both are pinned by test.

## B4 — Built

`send_deadline_seconds` (default 30 s; `null` = the old unbounded ladder), computed **once
per `send()`** in `_send_to_all_chats` so three channels cost one deadline rather than
three, and threaded through all three blocking parts:

- `_SlidingWindowRateLimiter.acquire(timeout=None) -> bool` — returns `False` instead of
  spinning, and never sleeps past the deadline (a 0.2 s budget must not cost a 0.5 s poll);
- the HTTP timeout is clamped to `min(timeout_sec, remaining)`;
- every backoff / `Retry-After` sleep goes through `_sleep_bounded`.

# C. M-S3 — STEP TIMEOUT

## C1 — What a step timeout does to its caller today

`screening/step_executor.py:116-133`, quoted:

```python
future = self._executor.submit(fn, signal, market_data, thresholds, direction)
score  = future.result(timeout=self._step_timeout_sec)
except FutureTimeoutError:
    ...
    step_results[name] = 0.5      # neutral score
    step_statuses[name] = "TIMEOUT"
    latencies_ms[name] = elapsed
    continue
```

`run_all()` does not raise — the step scores neutral 0.5, is marked `TIMEOUT`, and the loop
moves on. That is the *intended* reading. It is not what happens.

## C2 — ⭐ It bounds NEITHER the step NOR the caller

`future.result(timeout=…)` abandons the **wait**, not the **work**. Python cannot interrupt
a running function, and `future.cancel()` is a no-op once a task has started. Combined with
FIX-100's decision to share **one `max_workers=1` executor across every `run_all()` call**
(`:66-70`), a timed-out step keeps the only worker. Therefore:

1. every **remaining step of the same signal** queues behind the hung task and times out in
   turn ⇒ the caller pays **10 × the timeout**, not 1×;
2. every **later signal** queues behind the same hung task ⇒ the screening pipeline is
   serialized and never recovers;
3. `latencies_ms` is taken around `submit()+result()`, so it measures **queue wait**, not
   step time.

So the answer to C2 is worse than the question supposes: a single slow step consumes not
just this caller's whole budget but every subsequent caller's too. **The RED run showed it
literally** — one injected hang turned all ten steps into `TIMEOUT`.

## C3 — ⭐ REACHABLE IN PRODUCTION? **NO — INERT, and this is measured**

`screener_results.latencies` persists the real per-step numbers. Read-only, over a copy of
the live DB, **33,171 rows / 287,600 individual step measurements, 12-Jun → 24-Jul**:

```
p50     =      0.102 ms        rows with ANY step >= 1000 ms : 0  (0.0000%)
p90     =      0.221 ms        rows with ANY step >= 2000 ms : 0
p99     =      0.712 ms        rows with ANY step >= 4900 ms : 0
p99.9   =      1.756 ms        timeout signature (>=4900ms AND score 0.5) : 0
p99.99  =     10.370 ms
p100    =     66.061 ms        <-- the slowest step EVER, vs a 5,000 ms timeout (76x margin)
```

Per-step maxima span 4.02 ms (`signal_age`) to 66.06 ms (`rsi_range`). **The timeout has
never fired.**

That agrees with the structure: all ten step bodies are pure dict and float arithmetic —
no I/O, no network, no lock, no DB — and `now_ist()` is `datetime.now(tz=_IST)`. There is
no mechanism inside a step that can block for five seconds. The only theoretical route to
a timeout is queue wait behind an already-hung step, which requires a hung step to exist
first. **Same verdict shape as M-O9: real as a code property, unreachable in production.**

## C4 — Built anyway, labelled INERT

The fix **rotates** the poisoned pool rather than pretending the task was cancelled: on a
timeout, install a fresh single-worker executor and let the stale one go via
`shutdown(wait=False, cancel_futures=True)`, which returns immediately. The remaining steps
of this signal and every later signal then run normally. `run_all()` snapshots the pool it
submitted to, so it retires *that* one and not whichever a concurrent signal worker has
since installed; the swap and `shutdown()` share one lock.

Trade-off stated plainly: a genuinely never-returning step would hold up interpreter exit —
**unchanged from today**, where it also holds the pipeline forever. Strictly better, not
free.

**Deliberately NOT done:** `future.cancel()` (a placebo here), and **deleting the thread
pool altogether**. The pool cannot deliver the protection it advertises against pure-CPU
steps, so removing it is arguably the correct end state — it would also make `latencies_ms`
true step time and save ten thread hops per signal — but it removes the `TIMEOUT` status
and is a design call for Rama. **Recorded, not acted.**

**RED-first:** 3 defect tests red on HEAD, 5 pins green before and after (TIMEOUT still
scores 0.5, is not an error, is not the rejection point; the clean run and the v3
`exclude_steps` path untouched). Blast radius 97/97. **PARITY:** one code path, no mode
branch. **PUSHED.**

## D1 — What it actually is, from the writer and from real data

**The writer is broken as filed — and it never executes.**

```
data/live_feed.py:290    "volume": raw.get("volume_traded"),      # Kite: CUMULATIVE day volume
data/candle_store.py:63  self.volume += volume                    # summed per tick
```

Summing a cumulative series per tick yields neither cumulative nor delta — it is
meaningless. But three independent layers stop it from producing anything:

1. **MODE_LTP.** `live_feed.subscribe()` sets `KiteTicker.MODE_LTP` (`:182`); an LTP tick
   carries no `volume_traded`, and `main.py:2543` does `vol = int(t.get("volume") or 0)`
   ⇒ **the accumulator always adds 0.**
2. **Nothing subscribes.** `live_feed.subscribe()` has exactly **one** production caller in
   the entire repo — `orders/order_placer.py:3393`, inside the exit-retry enqueue path. In
   ordinary operation no token is subscribed, so `on_tick` never fires, no accumulator
   exists, `_close_candles()` emits nothing, and the `main.py:3375 _persist_candle`
   callback is never invoked.
3. **Measured confirmation.** Every one of the **275,129** rows in production
   `analytics.candles` (19-Jun → 24-Jul) has a **space-separated** `ts` — the
   `fetch_daily_candles` format. Rows with `main.py::_persist_candle`'s ISO-`T` format:
   **zero**. `is_synthetic=1`: **zero**. The live tick-candle path has never written a row.

**And the data that IS there is DELTA, proven from the data rather than the field name:**
40 of 40 `(symbol, date)` groups tested are **non-monotonic** across the session
(0 monotonic) — a cumulative series cannot decrease. Sample:
`AARTIIND 2026-07-15 → [4341, 8305, 4594, 4024, 6453, …]`. The 35,019 zero-volume rows are
genuine quiet minutes in illiquid names (NOCIL 13:30, CAPACITE 09:54), not the tick path.

## D3 — No live consumer. Sized, and held.

The only readers of the tick-built `CandleData.volume` are:

- `orders/smart_tgt_manager.py:392` — guarded by `self._volume_dependent_trails and
  candle.volume > 0`, where `volume_dependent_trails: false` in config **and** the block

- `main.py:3386 _persist_candle` → `analytics.candles.volume`, which per (3) above has

**Size of the fix if ever wanted:** two lines — keep the previous tick's cumulative
`volume_traded` per token and store the difference, plus switching the subscription to
`MODE_FULL` (or `MODE_QUOTE`) for the tokens that need it. **NOT DONE**, because it is
inert three times over and because flipping the subscription mode is a live-feed bandwidth
and rate-limit decision, not a bug fix.
