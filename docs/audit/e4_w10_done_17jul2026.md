> This changes **when the daily-loss limit fires**. It now fires on the **TRUE net**, which on

## 1 — What was wrong

E4 and W10 were **one bug**: the writer and the reader disagreed about what
`fm_ledger.pnl_delta` means.

| | |
|---|---|
| **WRITER** `fund_manager.release_used` | `pnl = gross_pnl - costs` → `pnl_delta` (**NET**), with `costs` stored alongside |
| **READER** `state_store.get_daily_realized_net_pnl` | `SUM(pnl_delta) - SUM(costs)` — on the false premise, asserted in its own docstring, that `pnl_delta` was **gross** ⇒ **costs subtracted TWICE** = **W10** |
| **WRITER** the 3 **backstop** close paths | `costs=0.0` hardcoded because neither class was ever wired a `CostCalculator` ⇒ their `pnl_delta` was **gross** = **E4** |

Two errors in **opposite directions** that do **not** cancel: 119 live rows overstate the loss,
36 understate it. On 16-Jul the control saw **−4.01 against a true net of −2.62** (53% too big).

**Both halves of the dual daily-loss mechanism read the same broken function** — the post-close
breach (`fund_manager.py:1279`) *and* the pre-trade RE7 gate (`risk_engine.py:25` via
`get_snapshot`). Fixing either half alone is a regression, which is why this is one commit.

## 3 — The migration

**The contract, now stated in the code:** `pnl_delta` is **NET**; `costs` is persisted for
**observability only** and is **never re-subtracted by any reader**.

| # | Change | File |
|---|---|---|
| a | reader → `SUM(pnl_delta)`; false docstring corrected | `core/state_store.py` |
| b | `round_trip_costs_or_zero` — one wiring helper, one fail-open policy | `broker/cost_calculator.py` |
| c | CHECK1 `:1109` + CHECK4 partial `:1901` → real costs; `cost_calculator` injected | `orders/order_reconciler.py` |
| d | GTT close `:450` → real **CNC** costs; `cost_calculator` injected | `orders/cnc_gtt_monitor.py` |
| e | `record_manual_close_financials` / `record_gtt_close_financials` accept `gross_pnl` | `core/state_store.py` |
| f | `release_used` persists `trade_id`; contract documented on the writer | `capital/fund_manager.py` |
| g | inject the shared calculator into both constructors | `main.py` |

**Simpler than the instruction assumed:** `product` is already in scope at both reconciler call
sites (`:1082`/`:1873` derive `intent` *from* it), so **no `ProductResolver` injection was
needed** — only the `CostCalculator`. The GTT path is `CNC` by construction. The partial path is
costed on the **closed slice only** (the remainder is costed when it closes).

**Cost source — reused, not reinvented:** `CostCalculator.total_round_trip_cost(...)` (CC12),
which *is* `round_trip_breakdown(...).total` — the same computation `order_placer:2301` uses.
`order_placer` needs the itemised breakdown for its per-trade cost columns; the backstops need
only the total. No parallel cost logic exists.

**Parity (Rule #5/#8) — free, and asserted:** `main.py:1786` builds the calculator from config
rates **before** `if args.mode == "paper"`. One mode-agnostic instance, injected into both
constructors. There is **no mode branch anywhere on this path**.

### The fail-open decision (investigation item #4 — silent `charges=0.0`)

A cost-calculation failure **degrades to `costs=0.0` and logs LOUDLY**; it does **not** raise.

**Rationale:** on a backstop path a raised exception would abort the capital release, stranding
the closed position's margin in `used` for the rest of the session (starving sizing) — strictly
worse than booking a slightly-wrong cost. This mirrors `order_placer`'s existing policy
deliberately: **one policy, not two**. The residual is stated honestly: such a row reverts to
pre-E4 **gross** for that one close, and says so in the log (`cost_calc_failed` /
`cost_calc_unavailable`), so it is attributable rather than silent.

## 5 — The historical gap (NOT backfillable — no backfill attempted)

The 36 live `costs=0` rows were written **gross**. Their real costs were **never computed**, so
they cannot be recovered from the DB — any backfill would be a fabrication. Under the new reader
they are read as NET, i.e. they **understate** those closes' true cost by ≈₹18 (an *estimate*,
from the ₹0.506 mean cost/close).

**This is bounded and self-clearing:** the daily-loss control is **per-day**, and `RESET_PNL`
zeroes it nightly. Only rows written *today* can affect today's control, and from the first boot
on the new code every row is NET. The gap is a **reporting-history** artifact, not a live control
artifact.

**One deploy-timing edge, stated for completeness:** if the deploy lands *after* today's EOD
`RESET_PNL` row was written under the old semantics, the new reader would read that day as
`Σ costs` (a small positive) rather than 0 for the remainder of the day. Positive ⇒ no breach ⇒
harmless, and it is post-close so nothing trades. From the next day it is moot.

## 7 — One flaw found in this change's OWN code (self-review, fixed before commit)

The first draft passed `product or "MIS"` into the calculator. `CostCalculator` accepts only
MIS/CO/CNC and **raises on NRML** — which `PRODUCT_TO_INTENT` maps to DELIVERY, i.e. it would pass
the reconciler's `intent` guard. The `or "MIS"` would have **silently costed an unexpected product
at MIS rates** — a wrong number, quietly, which is the precise bug class this commit exists to
remove. Changed to pass `product` through as-is so an unsupported product **fails open and
loudly** instead. Pinned by `test_unsupported_product_fails_open_rather_than_mis_costing`.

**NRML is unreachable on these paths today** (verified): `config/system_config.yaml` `product_map`
emits only `MIS`/`CNC`/`CO`, and `orders.product` — the column the reconciler's JOIN reads — is
written by our own placer from that map. NRML exists in `PRODUCT_TO_INTENT` purely as a defensive
reverse-mapping. The test pins the behaviour in case that ever changes.
