# What breaks if the service stays up until 17:35?

**READ-ONLY investigation.** 2026-07-24 (IST). Deployed HEAD: `bc75406`. Code + config + registry read; DB `mode=ro&immutable=1`. No change of any kind. Question: is it safe to move `SERVICE_WINDOW_END` from 16:00 to 17:35 so the 17:00 PB-01 Chartink alert lands on a live receiver?

**Standing-rule-5 caveat, up front:** the state "service alive 16:00–17:35" has **never existed** in the system's history. The service already runs **15:30→16:00** every trading day (≈30 min post-market, clean), so behaviours that resolve inside 30 minutes are effectively tested; the **extra ~95 minutes are not**, and where a conclusion rests only on code gates it is labelled ASSUMED, not MEASURED.

---

## VERDICT (the three answers)

> **1. NOT UNTIL one monitored extended session confirms it.** The analysis finds **no structural blocker** — every kill trigger is either market-hours-gated or needs ticks/orders/positions that do not exist post-market, the shutdown moves benignly, and the cron/DB concurrency is the *same WAL pattern already proven all day*. But per §1's decision rule, one component would run in a genuinely un-observed state: the **order-reconciler** (always-on, broker-calling, soft-kill-capable) polls every 15 s through the whole window, and its behaviour over the extra 95 minutes **cannot be verified by reading code** — only watched. So extend for **one** monitored day and confirm before trusting it; this is a light, observable precondition, not a code fix.
> **2. What would newly happen, each marked:** the [16:00,17:35) crons run against a *live* DB instead of an idle one — **BENIGN** (WAL concurrency; the identical reader+writer pattern already runs all market day via the GUI + the `*/5 09-15` crons); `wal_checkpoint`@16:00 runs against a live writer — **BENIGN** (it is PASSIVE); a post-market websocket disconnect may emit a WARNING — **BENIGN** (already downgraded off-hours, no kill); shutdown (WAL checkpoint + `cancel_all_entry_orders` + SHUTDOWN event) moves to 17:35 — **BENIGN** (cleanup only; nothing to cancel post-squareoff); WAL grows ~95 min longer before checkpoint — **BENIGN** (post-market writes are minimal); the 17:00 alert is captured — **the goal**. The one **NEEDS-OBSERVING**: the order-reconciler's 95 extra minutes of broker polling.
> **3. What could newly halt it: nothing HARD; one SOFT, and only if the reconciler newly fails.** Every enumerated trigger is inactive post-market (below). The sole residual is a reconciliation/capital-drift **SOFT_KILL** from the order-reconciler — which, if it fired at ~16:30, persists overnight and **auto-clears at the next 08:15 boot** (noisy, harmless; the service is exiting at 17:35 anyway). A flat book makes it unlikely, and the 30-min-clean window supports it, but the extra 95 min is ASSUMED, not measured.

---

## §2 — The shutdown path (what the 16:00 exit does)

Full reverse-order sequence (`main.py:1232-1445`, MEASURED): `_shutdown_event.set()` → drain HARD_KILL flatten worker → (conditional token invalidate) → `webhook_receiver.stop()` → `signal_proc.stop()` → stop sr_detector / regime / allocator / **v3_chain / pb01_entry_stage / pb01_capture_worker** / retest / structure_exit / zone_warmer → `entry_gate.stop()` → `smart_tgt.stop()` → `tgt_retry.stop()` → `order_reconciler.stop()` → **`order_monitor.cancel_all_entry_orders()`** → `order_monitor.stop()` → clock_skew / token_monitor stop → `live_feed.disconnect()` → `candle_store.stop()` → notifier "System Stopping" → **`insert_system_event("SHUTDOWN")`** → **PASSIVE `checkpoint_wal()`** → `store.close()`.

- **§2.2 — no daily bookkeeping lives here.** The only writes are a SHUTDOWN event row + a passive WAL checkpoint — *cleanup*, not day-state. The daily P&L reset / `_fired_for_date` are **clock-driven** at ~15:17 (§5.2), not exit-driven, so they do not move. `cancel_all_entry_orders` (:1382) finds nothing at 16:00 or 17:35 (no pending entries after the 15:17 squareoff + the [10:00,15:00) entry window). Moving all of this 95 min later is **BENIGN** (MEASURED).
- **§2.3 — "not flat at 17:35" is unchanged.** The exit gates on "past window AND flat" and, per M-C8, holds open while a HARD_KILL flatten runs (`main.py:1134-1175`); a non-flat book keeps it up past 17:35 exactly as it does past 16:00 today — same behaviour, later time. Not worsened. (MEASURED.)
- **§2.4 — restart is unaffected.** A clean exit 0 at 17:35 is identical to one at 16:00: systemd `Restart=on-failure` does not restart on 0, and the token-watcher/08:15 chain re-boots next morning regardless of the exit minute. (MEASURED from the exit path; the exit-code semantics are unchanged.)

## §3 — The cron window 16:00–17:35 (was "fine" with the service DOWN)

Jobs in the window (registry): `wal_checkpoint`@16:00, `generate_screened_csv`@16:01, **`daily_report`@16:05**, `daily_trade_review`@16:07, `trade_journal`@16:10, `compute_strategy_metrics`@16:15, `metrics_summary`@16:16, `gemini_log_review`@16:20, `strategy_registry_officer`@16:22, `gemini_trade_coach`@16:40, `gemini_data_integrity_check`@17:00. (`liveness_probe` stops at 15:55 — gated to [09:00,16:00) by its `*/5 09-15` schedule, so it does **not** false-alarm on the extended service; `forward_shadow_record`@18:15 runs after 17:35 either way — §5.3.)

- **§3.2 — the 16:05 daily report reads consistently and cannot be blocked.** It is a *reader*; the DB runs in WAL mode, where a reader takes a **consistent snapshot** and **never blocks, and is never blocked by, the writer** — that is the defining property of WAL. Crucially this is **not a novel interaction**: the *same* reader-against-a-live-writer pattern already runs every market day (the GUI dashboard on `:8500` and the `*/5 09-15` intraday crons read while the service writes). So the report reads a consistent snapshot at 16:05 exactly as the GUI does at 11:05. **BENIGN** (MEASURED — the concurrency pattern is exercised daily; the 16:05-specific timing is the only new part, and WAL semantics make it identical).
- **§3.3 — no instance-lock collision.** The service holds `/tmp/…/trading-system.lock` (fcntl) + binds `127.0.0.1:5001` (`utils/instance_lock.py`), acquired by `main.py` and by the operator tool `clear_kill_switch.py` only. **No job in the window acquires either** (grep-verified — they are read/compute jobs). **BENIGN** (MEASURED).
- **§3.4 — no job assumes exclusive access.** `wal_checkpoint` is **PASSIVE** (`wal_checkpoint.py:4,33` — co-exists with a live writer, just checkpoints fewer frames); no VACUUM runs in the window (the Sunday `db_retention --vacuum` is 02:30). The writing crons (`trade_journal`, `compute_strategy_metrics`, `strategy_registry_officer`) serialize with the service's writes via the WAL write-lock + busy_timeout — the *same* serialization the `*/5` `capture_metrics` writer already uses intraday. Post-market the service writes rarely, so contention is brief. **BENIGN** (MEASURED pattern; the specific jobs are ASSUMED to inherit it).
- **§3.5 — nothing reads "is the service running" as a signal** in the window (the one that does, `liveness_probe`, is gated out by 15:55). (MEASURED.)

## §4 — The feed and the kill switch (the highest-risk area — and it is gated)

Today the service already runs ~30 min post-market; the proposal makes it ~125 min. Every trigger:

- **§4.1 — feed tick-age watchdog: `tick_stale_threshold_sec = 30 s`, but market-hours-GATED.** `_watchdog_loop` skips when `not is_entry_allowed(now_ist())` (`live_feed.py:715-718`) — it explicitly "Skip[s] when outside market hours so off-session restarts do not keep firing alerts." The entry window ends ~15:00–15:30, so the watchdog is **already silent 15:30→16:00 today** and stays silent to 17:35. The 30 s threshold is moot post-market — it does **not** newly fire. (MEASURED.)
- **§4.2/4.3 — reconnect exhaustion: post-market is a WARNING, NOT a kill.** `max_reconnect_attempts=10 × 5 s`; on exhaustion `_on_max_reconnect` computes `during_market = is_market_open(now_ist())` and, when off-hours, "**not escalating (no SOFT_KILL / no CRITICAL)**" — downgrading to one WARNING (`live_feed.py:440-461`). The code comment names the exact precedent: the "07:07 KiteTicker max reconnect exhausted CRITICAL **while the service was (wrongly) running overnight**" — i.e. this gate was built *because* the service sometimes runs post-market. So the design already anticipates the proposed state. **BENIGN** (MEASURED).
- **§4.3 — the other feed triggers need ticks/threads that don't exist post-market:** the queue-full `soft_kill("LIVEFEED_QUEUE_FULL")` needs incoming ticks to overflow (none post-market); `_check_consumer_health` soft-kills only if the consumer thread is **dead** (post-market it is idle-blocked on an empty queue, not dead — and it already runs cleanly 15:30→16:00). **BENIGN** (MEASURED for 30 min; the idle-thread conclusion is ASSUMED for 125).
- **§4.4 — token monitor: market-hours-GATED, and SOFT not HARD.** It "Polls `kite.profile()` every 1800 s **during market hours**" (`broker/token_monitor.py:11,167-172`), and on expiry SOFT_KILLs (TM2), never HARD (TM3). Post-market it does **not** poll, so it cannot fire even if the token lapsed. The token is refreshed 08:15 and only deleted 05:00, so it is valid through 17:35 anyway. **BENIGN** (MEASURED).
- **clock-skew probe:** soft-kills only on a *genuine* critical clock skew (`clock_skew_probe.py:10,37`) — time-of-day-independent, already running 15:30→16:00; not a new post-market trigger. **BENIGN**.
- **API-failure → HARD_KILL (order-monitor):** needs failing order-API calls; post-market there are no pending orders to poll → no calls → cannot accumulate. **BENIGN** (MEASURED — no pending orders post-squareoff).
- **§4.5 — the one always-on, un-gated, kill-capable timer: the ORDER-RECONCILER.** A 15 s daemon poll (`order_reconciler.py:13`) that is **not** market-gated, makes broker position/margin calls every cycle, and SOFT_KILLs on a run of reconciliation failures (RC13, `:41`); a capital-drift path alerts on a 30-min interval (`:346-353`). A **flat** post-market book reconciles clean, and it runs clean 15:30→16:00 today — but over the extra 95 minutes it issues ~380 more broker calls in a state that has **never existed**, and a post-market broker settlement/margin update or an API wobble could, in principle, trip a **SOFT_KILL** (auto-clears at the next boot). ⚠️ **This is the one thing that cannot be measured from code (standing rule 5); it is why the verdict is "NOT UNTIL a monitored session," and it is soft, not hard.**

## §5 — Is 16:00 a day boundary for anything?

- **§5.1 — nothing keys off the SERVICE EXIT (enumerated, not asserted):** the day-state resets (P&L, `_fired_for_date`, RESET_PNL) fire on the **clock** via `eod_squareoff.check_and_fire(now_ist())` at ~15:17, keyed on the calendar date (`eod_squareoff.py:17-18,196-224`); the crons fire on their own cron times; the self-exit only sets a shutdown event. No latch/counter/reset observed that triggers *on the exit* rather than a clock time. Moving the exit moves none of them. (MEASURED.)
- **§5.2 — confirmed clock-driven** (above): 15:15 circuit-breaker / 15:17 squareoff, unaffected.
- **§5.3 — the 18:15 forward-shadow recorder** runs after 17:35 either way, against a **closed** DB (the service has exited by 17:35) — so no contention with a live writer (unchanged). (MEASURED.)
- **§5.4 — WAL / handles / memory over the extra 95 min:** post-market there are no ticks and no trades, so writes are limited to heartbeats/monitor rows — WAL growth is small and is bounded by the 16:00 passive checkpoint and the 17:35 shutdown checkpoint; open handles/threads are the same daemon set already alive; nothing observed as unbounded. **BENIGN** (rough sizing, ASSUMED — not a deep study).

## §6 — Recorded correction (NOT a task; §6 of the brief)

⭐ **The `pb01_simulation_feasibility_2026-07-24.md` conclusion "the candidate universe cannot be reconstructed / ~zero candidates" is corrected.** The universe was absent *from the system's held data* (0 `pb01_watchlist` rows, 0 `pb01_breakout_retest` signals) **because all ten 17:00 alerts hit a dead port** (service exited 16:00) — not because the candidates don't exist. **They exist in Chartink's trigger history: ten trading days since 13-Jul, ~7–34 symbols each (~17/day), with dates and symbol lists, exportable as CSV.** Caveats recorded so the correction does not overshoot: **(a)** backfilling the watchlist from that history would be a **BACKTEST, never out-of-sample** — a row created today for a 13-Jul breakout is retrospective by definition; **(b)** outcome data may be missing — the held 1-minute candles cover only the 482 momentum-tracked symbols, and the PB-01 triggers name *different* stocks, so the overlap (how many PB-01 symbols have held candles) is unknown and worth counting one day. ⛔ **Do not act on this** — it is a separate decision.
