## 1. The change (three edits, one inseparable fix)

`signals/webhook_receiver.py` — 48 lines, mostly comment. No schema change. No config change.

| # | Where | What |
|---|---|---|
| 1 | `:58-65` (new) | `_RETRYABLE_STATUSES = frozenset({"QUEUE_FULL", "STORE_ERROR"})` — the statuses meaning *"not taken, not a duplicate, send it again"*. |
| 2 | `_process_signal:904-931` (new) | `except Exception` **beside/after** `except sqlite3.IntegrityError` — releases the dedup cache claim **and** the in-flight claim, logs CRITICAL, returns `STORE_ERROR`. |
| 3 | `_process_request:657-661` | the 503 predicate `any_queue_full` → `any_retryable` (membership in `_RETRYABLE_STATUSES`). |

Plus the `WR10` docstring line, which enumerates the per-signal statuses.

**Handler ordering is load-bearing:** `except sqlite3.IntegrityError` stays **first**, so
Python matches it before the broad clause and `IntegrityError → DUPLICATE` is byte-for-byte
unchanged. Verified in the file (`:869` before `:904`) and by the untouched IntegrityError
tests.

## 2. Why release + retryable are ONE fix, not two

This is the trap the investigation flagged, and it is real. The two halves fail separately:

| | claim | HTTP | outcome for the signal |
|---|---|---|---|
| **pre-fix** | held | **500** (exception escapes to `_handle_webhook:427`) | retry arrives but is **bounced** by the leaked claim → dropped, ≤300 s |
| **release only** (the trap) | released | **200** (`:650` only knew QUEUE_FULL) | **no retry is ever sent** → dropped **permanently** — *worse than the bug* |
| **shipped** | released | **503** | retry arrives **and** gets through → recovered |

Catching the exception is what *removes* the old 500, so catching without restoring a
retryable code would have introduced the permanent loss. That is why this is one commit.

## 3. Batch-continue (§2c) — confirmed

`_process_request:637` calls `_process_signal` inside the per-symbol loop with **no
try/except**, so a raising store failure abandoned every symbol *after* the failing one.
Returning instead of raising keeps the loop alive. Proven by
`test_p3s14_store_failure_does_not_abandon_rest_of_batch`: payload `RELIANCE,TCS,INFY` with
the INSERT failing **only for TCS** (deliberately in the middle) →
`{RELIANCE: ACCEPTED, TCS: STORE_ERROR, INFY: ACCEPTED}`, and INFY — the symbol *after* the
failure — is verified **actually stored in the DB**, not merely reported.

## 4. Preserved contracts (§2d) — each checked, not assumed

| Contract | Where | Status |
|---|---|---|
| 503-at-queue-full | `:648-650` | **preserved** — QUEUE_FULL is still in the predicate, now via set membership |
| `X-Queue-Depth` / `X-Queue-Warning` | `:656-660` | **untouched** (computed after the predicate, unchanged) |
| QUEUE_FULL row re-accept + `signal_id` reuse | `:869-890` | **untouched** — inside the IntegrityError handler, which still matches first |
| in-flight release on every reject | `:821/:877/:891/:915` | **untouched**; the new path adds a fifth release |
| `signal_processor` releases the ACCEPTED path | `:918-919` | **untouched** — no accepted path changed |
| `IntegrityError → DUPLICATE` | `:858` | **untouched** (ordering verified) |

**No double-entry is re-opened** (the §6 STOP condition — checked in code, not assumed).
Releasing the cache is safe because the cache is *not* the control:

1. `_claim_in_flight` (`:822`) still serialises concurrent same-symbol requests — and it is
   checked **before** the dedup cache, so it is the first thing a retry meets.
2. `UNIQUE(fingerprint, fingerprint_date)` (`schema.sql:82-83`) remains the authoritative
   within-window dedup: a retry inside the same 300 s bucket recomputes the **same**
   fingerprint → `IntegrityError` → `DUPLICATE`. A retry landing in the next bucket is
   ≥300 s later, i.e. exactly when the cache would have expired anyway.

The failed INSERT rolls back, so there is **no orphan row** to collide with — asserted
directly in two of the three tests.

**`STORE_ERROR` never reaches the DB.** Its INSERT is what failed, so no row exists; the
status appears only in the response body. Confirmed against the two places that would
otherwise care:
- `core/schema.sql:60-66` — the `CHECK (status IN (...))` constraint on `signals.status`
  needs **no new value**, hence no schema change.
- `reports/daily_trade_review.py:717` `_KNOWN_OTHER_STATUSES` — an unmapped status would
  make the SIGNAL-STORAGE reconciliation Δ ≠ 0 (a real schema-drift alarm). `STORE_ERROR`
  cannot appear there, so the reconciliation is unaffected.
  (`ops_dashboard/.../db_reader.py:466-469` likewise classifies DB statuses only.)

**The test gap that hid this is closed**: no webhook test injected a non-`IntegrityError`
INSERT failure. The new harness (`_InsertFailingCursor` + `_insert_fails_for`) raises
`sqlite3.OperationalError` at the real `cur.execute("INSERT INTO signals ...")` **inside the
real transaction**, so the real `BEGIN IMMEDIATE`/`ROLLBACK` still run
(`state_store.py:534-541` re-raises after rollback) — the failure is injected at the
INSERT, not simulated around it. Keying the injection on the symbol is what lets the same
mechanism drive both the single-signal and the mid-batch cases.

## 6. ⭐ Two premises were wrong — corrected by evidence

Both the instruction (§3) and the investigation state the pre-fix symptoms in ways the
runtime disproves. Neither changes the fix — both claims leak, both must be released, and
both are — but the record should be right ([[feedback-verify-the-finding-premise]]).

**(a) Pre-fix the response is `500`, NOT `200`.** The instruction's RED-on-old expectation
("response 200") describes the *trap* (what a naive release-only fix would produce), not the
old code. Old code raises, and the exception escapes to `_handle_webhook:427` → CRITICAL →
**500**. Proven: `AssertionError: expected 503, got 500`. The tests are still RED-on-old —
just for the right reason. (The investigation states this correctly in Q4-c; only the
instruction's §3 parenthetical is wrong.)

**(b) An IMMEDIATE retry is bounced as `IN_PROCESS`, not `DUPLICATE`.** Both documents say
"DUPLICATE-bounced" throughout. But `_claim_in_flight` (`:822`) is checked **before** the
dedup cache (`:829`), and *both* claims leak — so the retry never reaches the dedup check.
Proven: `assert 'IN_PROCESS' == 'ACCEPTED'`. The real sequence on pre-fix code is:

| Retry lands | Bounced as | By |
|---|---|---|
| 0 → ~120 s | **`IN_PROCESS`** | the leaked in-flight claim (sweeper clears it, ≤120 s) |
| ~120 → 300 s | **`DUPLICATE`** | the leaked dedup cache claim |
| after 300 s | *accepted* | TTL expired |

The investigation's headline conclusion is unaffected: the dedup cache is still the binding
constraint and the loss is still bounded to **~300 s**. Only the *name* of the immediate
symptom changes — which matters if anyone ever greps for the bounce in anger.

## 7. ⚠️ The ops fingerprint changes (deliberate, inherent to the design)

The investigation's evidence rests on `response_code=500` being this bug's fingerprint
(**0 × 500 in 89,794 POSTs**). **After this fix that fingerprint no longer exists** — a store
failure now answers **503**, which `webhook_audit` cannot distinguish from QUEUE_FULL
backpressure (18 such rows in the same period). That is unavoidable: any retryable status
must yield a retryable code.

So the CRITICAL log line is now the thing to alert on, and it is deliberately distinct and
greppable:

```
webhook_receiver: signal store FAILED for <scanner>/<symbol>: <exc> -- claims released, returning STORE_ERROR so the sender retries
```

**CRITICAL, not ERROR, on purpose**: pre-fix this reached `_handle_webhook`'s CRITICAL.
Catching it must not make a real incident *quieter* than it was. Severity is preserved;
only the channel moves (audit-row code → log line).

Also unchanged-by-design: a 503 batch writes `accepted=0, rejected=0` to `webhook_audit`,
because `_handle_webhook:416` only extracts counts from 200s. That is the pre-existing
QUEUE_FULL 503 behaviour, not a regression.

## 10. Scope

**Implemented exactly as approved.** Not done, deliberately: claim-after-insert re-ordering
(rejected in the investigation — re-orders a signal-entry path for no added safety); any
schema change; M-S4 / own-runs / Rama's area.

**Observation for the loop (NOT fixed here, out of scope):** the *same shape* survives one
line deeper. Inside the IntegrityError handler, `fetch_one` (`:875`) and the re-queue
`UPDATE` sit in the region between the claims and the return; an exception raised **inside**
an `except` block is not caught by a sibling `except`, so a failure there still escapes with
both claims held. It is materially narrower than the fixed path — reaching it requires the
INSERT to raise `IntegrityError` (proving the DB is healthy enough to enforce a constraint)
and *then* the very next SELECT to fail — and the `UPDATE` already has its own try/except.
Recording it rather than widening a signal-entry change beyond its approved design.
