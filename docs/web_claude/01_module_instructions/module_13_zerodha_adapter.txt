ZA3 — Rate limiter integration:

  Category map (lock):

    get_positions, get_margins -> "margins"
    get_quote -> "quote"

ZA4 — Product resolver integration:
  place_order receives semantic intent (INTRADAY/DELIVERY/etc.).
  Adapter calls product_resolver.resolve(intent, "zerodha")
  to get broker code BEFORE building the kite request.
  Reject unknown intent -> ProductNotSupportedError bubbles up.

ZA5 — Error mapping (exception translation table):
  HTTP 403 / "TokenException" -> BrokerAuthError
  HTTP 5xx / requests.Timeout / socket.timeout -> BrokerTimeoutError
  Kite "InputException" with "rejected" -> OrderRejectedError
  Kite "OrderException" -> OrderRejectedError
  Kite "NetworkException" -> BrokerTimeoutError
  Kite "GeneralException" -> BrokerError (base)
  Any other unknown exception -> BrokerError, log full traceback

ZA6 — OrderRejectedError context (lock):

ZA7 — Internal order ID:
  Adapter calls new_order_id() (from core.ids) at start of
  place_order. Registers with state_machine in PENDING.
  After successful kite call, transitions to SUBMITTED.
  On kite exception, transitions to FAILED.
  Returns PlacedOrder with BOTH internal_order_id and
  broker_order_id (the kite response order_id).

ZA8 — State machine integration on every place_order outcome:
  Success path: PENDING -> SUBMITTED
  Exception path: PENDING -> FAILED
  cancel_order: caller is responsible for state transition
                AFTER getting CancelResult (adapter does NOT
                auto-transition because cancel may be partial).

ZA9 — Logging contract:
  Every method entry: logger.info("call_start", extra={method, args_redacted})
  Every method exit: logger.info("call_end", extra={method, duration_ms, result_summary})
  Every exception: log_exception(logger, exc) before re-raise.
  No request bodies logged (PII / API key risk).

ZA10 — Paper mode:

    place_order: skip kite, generate fake broker_order_id
                 ("PAPER_" + uuid4 hex 12 chars), simulate
                 immediate SUBMITTED state, return PlacedOrder.

    modify_order: always success, never calls kite.

  Same interface, same return types, same exceptions possible
  (e.g., simulated rejection if qty <= 0).
