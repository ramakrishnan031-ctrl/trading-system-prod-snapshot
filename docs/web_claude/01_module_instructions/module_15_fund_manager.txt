LOCK BEFORE BUILD:

FM1 — Purpose: Single source of truth for capital state.
  Holds: total_capital, available_capital, reserved_capital,
         used_capital, daily_realized_pnl.
  All capital mutations go through this module. No other
  module owns capital state. Replaces the 5+ scattered
  capital tracking points flagged in audit Part 3.1.

FM2 — Three-balance model (audit P7a):
  total_capital     = broker net (cash + holdings)
  available_capital = total - reserved - used
  reserved_capital  = sum of in-flight order margin requirements
  used_capital      = sum of filled position margin requirements
  Invariant: available + reserved + used == total
  Checked inside EVERY mutation transaction (audit G3).

FM3 — Bucket split (audit Issue #3):
  Capital allocated across two buckets:
    intraday_bucket  (default 70%)
    positional_bucket (default 30%)
  Each bucket has independent available/reserved/used.
  Bucket split percentages from system_config.yaml.
  Reservations and uses are bucket-scoped:
    INTRADAY/COVER_ORDER intent -> intraday bucket
    DELIVERY intent              -> positional bucket
  Cross-bucket borrowing FORBIDDEN (audit explicitly).

FM4 — Margin calculation (audit catastrophic flaw fix):
  required_margin = qty * price / leverage
  NOT qty * price (notional). Audit found system was deducting
  5x the actual margin blocked.
  Leverage by intent (lock; from system_config):
    INTRADAY      -> 5.0  (MIS leverage)
    COVER_ORDER   -> 6.0  (CO leverage)
    DELIVERY      -> 1.0  (CNC, no leverage)
    BRACKET_ORDER -> 5.0
  Module-level helper:
    required_margin(qty, price, intent, leverage_map) -> float

FM5 — Atomic reserve/release/commit (audit Issue #1, #24):
  All capital state changes wrapped in single threading.RLock.
  Snapshot + reservation in SAME atomic block. No "check then
  reserve" pattern that audit found exploitable.

  Public API:
    reserve(symbol, qty, price, intent, signal_id) -> ReservationResult
      - Atomically: compute margin, check bucket available,
        reserve if sufficient.
      - Returns ReservationResult(success, reservation_id, margin,
                                   bucket, reason_if_failed)
      - On success: available -= margin, reserved += margin
      - On insufficient: returns success=False with reason,
        does NOT raise.
      - Writes to capital_ledger via state_store (G3) inside
        same transaction.

    release(reservation_id, reason) -> bool
      - Atomically: available += margin, reserved -= margin
      - Used on order rejection / cancel.
      - Idempotent: releasing twice is a no-op (returns False
        second time, no exception).

    commit_to_used(reservation_id, actual_fill_price, actual_qty)
                  -> CommitResult
      - Atomically: reserved -= reserved_margin,
                    used += actual_margin (recomputed at fill)
      - Used on OrderFilled event.
      - Handles partial fills: actual_qty may be < reserved qty.
        Excess margin returns to available.

    release_used(symbol, exit_price, exit_qty, intent)
                -> ReleaseResult
      - Atomically: used -= margin, available += margin + pnl
      - Updates daily_realized_pnl by (exit_value - entry_value
        - costs).
      - Used on PositionClosed event.

FM6 — Reservation tracking:
  Each reserve() generates reservation_id (uuid4 hex 16 chars).
  Internal _reservations dict: {reservation_id -> {symbol, qty,
    margin, bucket, intent, ts, signal_id}}.
  Required for release() and commit_to_used() to know what to
  reverse.

FM7 — Daily loss limit (audit Issue #6):
  Tracks daily_realized_pnl. After every release_used(), checks:
    if daily_realized_pnl <= -daily_loss_limit:
      fire on_daily_loss_breach callback (constructor-injected)
  This is RECOVERED post-trade (audit flaw: monitors after exit).
  Intra-trade unrealized P&L monitoring is order_monitor's job.
  fund_manager is the realized side only.

FM8 — Snapshot API:
  get_snapshot() -> CapitalSnapshot
    Frozen dataclass with: total, intraday_avail, intraday_reserved,
    intraday_used, positional_avail, positional_reserved,
    positional_used, daily_realized_pnl, ts.
  Used by reporting, telegram, and risk_engine.
  ALWAYS taken under lock (consistent point-in-time view).

FM9 — Broker sync (audit Issue: double deduction fix):
  sync_from_broker(broker_balance: float) updates total_capital
  to match broker truth. Internal reserved + used are NOT
  touched (those are our tracking). Available is recomputed:
    available = total - reserved - used
  Audit flaw was subtracting used from broker balance after
  broker had already reduced it. Lock: NEVER subtract used
  from broker_balance. Broker balance is total. Our reserved
  and used are subtracted from total to get available.

FM10 — Capital ledger persistence (audit G3):
  Every mutation writes a row to capital_ledger table
  (already in state_store schema):
    {ts, mutation_type, amount, bucket, balance_before,
     balance_after, signal_id, reservation_id, reason}
  Inside same transaction as the in-memory mutation.
  If state_store write fails: mutation rolled back, exception
  raised. No silent in-memory drift.

FM11 — Invariant violation:
  After every mutation, before commit:
    if abs((available + reserved + used) - total) > 0.01:
      raise CapitalInvariantViolation(
        context={total, available, reserved, used,
                 expected_sum, actual_sum, mutation_type,
                 reservation_id})
  CapitalInvariantViolation already exists in core.exceptions.
  This is CRITICAL severity. Fires on_critical_failure
  callback before raising.
