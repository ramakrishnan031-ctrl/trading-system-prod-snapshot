    bus,                 # EventBus
    logger,
    poll_interval_sec=2, # from system_config.yaml
    fill_timeout_sec=60, # cancel-if-not-filled threshold
  )
  poll_interval_sec and fill_timeout_sec read from system_config.

OM3 — Track method:
  monitor.track(internal_order_id, broker_order_id, symbol,
                side, qty, expected_price, placed_at: datetime)
  Adds to internal _watched dict. Polling thread picks up.

OM4 — Polling thread:
  monitor.start() launches single daemon thread.
  Thread loops: every poll_interval_sec, iterates snapshot of
  _watched, calls adapter.get_order_history(broker_order_id) for
  each, processes status.
  monitor.stop() signals thread to exit, joins with 5s timeout.

OM5 — Status processing (Zerodha statuses to internal states):
  "OPEN" or "TRIGGER PENDING"  -> state OPEN
  "PARTIAL" or filled_qty > 0 and < qty  -> state PARTIAL
  "COMPLETE" -> state COMPLETE, emit OrderFilled
  "CANCELLED" -> state CANCELLED, remove from _watched
  "REJECTED" -> state FAILED, remove from _watched
  Unknown status -> log WARNING, no transition

OM6 — OrderFilled event payload (already in events.py;
  verify schema matches):
  {internal_order_id, broker_order_id, symbol, side,
   qty, avg_fill_price, expected_price, slippage_pct,
   filled_at: datetime}
  If schema differs, extend OrderFilled dataclass FIRST
  (update test_events.py).

OM7 — Fill timeout (audit Issue #14):
  If order in OPEN or SUBMITTED state for > fill_timeout_sec:
    1. Call adapter.cancel_order(broker_order_id)
    2. On cancel success: state SUBMITTED/OPEN -> CANCELLED
    3. On cancel failure: log CRITICAL, state -> FAILED,
       emit alert via on_orphan_callback (constructor-injected,
       optional). NEVER leave broker order open silently.
  Per audit: "Orphaned broker position" is CRITICAL severity.

OM8 — Partial fill handling (audit Issue #26):
  When status = PARTIAL with filled_qty > previous filled_qty,
  transition to PARTIAL (self-loop OK per OSM2). Track
  cumulative filled_qty in _watched entry. Emit OrderFilled
  ONLY on COMPLETE — partial fills update internal state and
  log INFO but do NOT emit OrderFilled (that's a final-state
  event).

OM9 — Slippage calculation:
  slippage_pct = (avg_fill_price - expected_price) / expected_price * 100
  For SELL: invert sign so positive slippage = unfavorable.
  For BUY: positive slippage = unfavorable (paid more than expected).
  Lock formula:
    BUY:  slippage_pct = (avg_fill - expected) / expected * 100
    SELL: slippage_pct = (expected - avg_fill) / expected * 100

OM10 — Thread safety:
  _watched dict guarded by threading.Lock.
  Polling thread iterates a snapshot (copy under lock,
  process outside lock). Avoids audit Issue (paper engine
  iterating dict while it changes).

OM11 — Backpressure / error tolerance:
  If adapter raises BrokerTimeoutError during poll: log,
  skip that order this cycle, retry next cycle.
  If adapter raises BrokerAuthError: log CRITICAL, stop
  monitor thread (auth is dead, no point polling).
  3 consecutive cycles with auth error -> call
  on_critical_failure callback (constructor-injected).

OM12 — Idempotency:
  Polling the same order multiple times must be safe.
  State machine rejects illegal transitions (already
  COMPLETE -> COMPLETE) — monitor catches
  InvalidTransitionError, logs DEBUG, continues. Not an
  error condition.
